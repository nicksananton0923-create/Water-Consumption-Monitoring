## 1. Executive summary

This repository delivers a complete, reusable system for recording,
validating, analyzing, and visualizing water consumption in an industrial
facility. The sample dataset simulates a textile factory with six
cumulative water meters across dyeing, washing, boiler, cooling tower,
process, and domestic utilities areas, observed daily across a full
calendar year. The total recorded and validated water consumption for the
sample period is approximately 61,000 m³, distributed unevenly across the
six meters in a pattern consistent with normal textile production.

The repository provides three dashboard surfaces — Excel, Python (PNG +
HTML), and a Power BI build guide — all driven from the same validated
CSV outputs. The Python validation pipeline (`scripts/data_validation.py`)
flags 14 potential issues across the sample year, including one missed
reading, one duplicate timestamp, one meter rollover, one negative delta,
and one statistical consumption spike. None of these flags are
classified as confirmed leaks; each is an investigation work-order
requiring on-site verification before any classification is made.

The system is intentionally conservative in its claims. It does not
infer leak locations, it does not calculate water savings without
evidence, and it does not auto-classify any anomaly. The role of the
dashboard is to surface patterns and irregularities for human review,
not to replace engineering judgment.

### What is included

- A complete, anonymized sample dataset (2,219 readings, 6 meters, 1 year).
- CSV templates for the meter register and the manual consumption log.
- A Python validation pipeline with five validation rules and statistical
  anomaly detection.
- Three dashboard surfaces: Excel (`.xlsx`), Python (`.png` + `.html`),
  and a Power BI build guide.
- A complete documentation set: data dictionary, calculation methodology,
  validation rules, dashboard guide, system architecture, hardware
  wiring, and this summary report.
- Three architecture diagrams (system, data flow, schema) as PNG and
  Mermaid source.
- An Apache 2.0 license for free commercial and academic reuse.

### What is explicitly excluded

- Real plant data: every reading in the sample is synthetic.
- Confirmed leak classifications: every flagged anomaly requires
  investigation before classification.
- Water savings claims: no savings are asserted in the absence of
  baseline-vs-intervention evidence.
- Hardware procurement: the repository does not endorse specific meter
  manufacturers or data loggers; it documents typical industrial practice
  only.
- Real-time streaming: the architecture is CSV-based; extension to
  streaming is documented but not implemented.

## 4. Calculation method summary

The core calculation is straightforward for cumulative meters:

```
delta_m3 = current_cumulative_reading − previous_cumulative_reading
```

computed per meter, in datetime order, considering only valid readings.
Daily, weekly, and monthly totals are sums of valid deltas within the
period. Targets are daily values defined in the validation script and
multiplied by the number of days in the period for weekly and monthly
target computations.

Negative deltas are flagged but not silently interpreted as rollovers.
The reviewer must inspect the meter register and operator notes to
determine whether the negative is a legitimate rollover (in which case
the actual consumption equals `rollover_limit − previous + current`), a
meter replacement (no delta should be computed across the replacement
boundary), or a manual entry error (the source should be corrected).

The complete methodology, including variance calculations, status
classification thresholds, and target validity rules, is documented in
`docs/calculation-methodology.md`.

## 5. Validation results

Running `scripts/data_validation.py` on the sample dataset produces the
following flag breakdown:

| Flag | Count | Description |
|---|---|---|
| `MISSING_READINGS` | 1 | Gap > 1 day between consecutive readings |
| `DUPLICATE_TIMESTAMP` | 1 | Two rows for the same meter at the same datetime |
| `NEGATIVE_DELTA` | 1 | Current cumulative < previous cumulative |
| `ROLLOVER_SUSPECTED` | 1 | Delta > 50% of the meter's rollover limit |
| `POTENTIAL_ISSUE` | 10 | Consumption > 3× the 14-day rolling median |

Total: 14 flagged rows out of 2,219 readings (0.63% flagged rate).

The `POTENTIAL_ISSUE` flags are mostly the rolling-median test firing on
the intra-day hourly readings for the dyeing meter on 2024-09-15, plus
the deliberate spike on 2024-06-22. This is expected behavior — the
statistical test detects any consumption that is statistically unusual
for that meter, regardless of cause. The classification (operational
surge vs. meter fault vs. leak) requires on-site investigation, which is
out of scope for the pipeline.

## 6. Dashboard outputs

### Excel dashboard (`dashboard/water-dashboard.xlsx`)

Six sheets:

1. README — quick-start instructions.
2. Meter Register — table of 6 meters with metadata.
3. Readings — 2,219 raw readings with live `Delta (m3)` formulas and
   conditional formatting (negative-delta cells highlighted red).
4. Daily Summary — 2,186 rows of per-meter daily consumption with target,
   variance, variance %, and a status label (`OK`, `HIGH`, `OVER`, `LOW`,
   `NO DATA`).
5. Monthly Summary — 72 rows of per-meter monthly totals with target,
   variance, and a color-scale heatmap on the variance % column.
6. Dashboard — KPI strip (4 KPIs) + three native Excel charts:
   - Line chart: daily consumption for the top 3 meters over the year.
   - Bar chart: total consumption by meter.
   - Column chart: monthly consumption by area.

### Python dashboard (`dashboard/python_dashboard.png`, `.html`)

Six-panel static image and an interactive Plotly HTML version with the
same KPIs plus an inline table of the first 15 anomalies. Suitable for
embedding in a GitHub README or a scheduled email report.

### Power BI build guide (`dashboard/power-bi-build-guide.md`)

A step-by-step guide to rebuilding the same KPIs in Power BI Desktop,
consuming the validated CSVs as the data source, with a recommended star
schema and DAX measures. Does not ship a `.pbix` file (the binary format
is not suitable for version control).

## 8. What has NOT been tested

- Performance on datasets larger than the sample (~2,200 rows). The
  pipeline uses pure-Python loops; for 100,000+ rows, consider migrating
  to pandas or DuckDB.
- Power BI dashboard refresh: the build guide is documented but a real
  Power BI workspace was not provisioned for this work.
- Live data acquisition from a real data logger. The repository assumes
  CSV ingestion; the gateway-to-CSV step is documented but not
  implemented in this repo.
- Mobile rendering of the Excel dashboard. Excel for iOS/Android has
  limited conditional-formatting and chart support; the dashboard may
  look degraded on a phone.

## 9. Recommendations for production deployment

1. **Replace sample data with real readings** in a private repository or
   local-only folder. Never commit real plant readings to a public repo.
2. **Replace placeholder daily targets** in `scripts/data_validation.py`
   with plant-authorized values. Targets without authorization are not
   meaningful for management reporting.
3. **Add a plant identifier column** to every table if you deploy this
   across multiple sites; the schema is single-plant by default.
4. **Schedule the pipeline** via cron (Linux) or Task Scheduler (Windows)
   to run after the nightly data export from the logger / SCADA system.
5. **Establish an investigation workflow** for every flagged row. A flag
   without an investigation record is not evidence of anything.
6. **Calibrate meters annually** and update the `calibration_due` column
   in the meter register. Meters out of calibration should be flagged as
   `status = 'out_for_calibration'` and excluded from variance reporting
   until recalibrated.
7. **Back up the raw CSVs and validated outputs** to a separate location
   (e.g., S3, Azure Blob) for audit and traceability. The git repository
   is for code, not for long-term data storage.

## 10. How to extend this repository

| Extension | Required change |
|---|---|
| Add a new meter | Add a row to `templates/water-meter-register.csv`; add to `METERS` in `scripts/generate_sample_data.py` (sample) or to the real source CSV (production) |
| Add a new validation rule | Add a function in `scripts/data_validation.py` and call it before writing outputs |
| Add a new KPI | Extend the KPI strip in both `scripts/generate_dashboard.py` and `scripts/build_excel_dashboard.py` |
| Switch to a database backend | Replace the CSV read/write in `data_validation.py` with SQL queries; keep the validation rules unchanged |
| Add real-time streaming | Replace the CSV step with a Kafka or MQTT consumer; keep the validation rules in the consumer |
| Translate the documentation | Copy each markdown file to a `*-ta.md` Tamil version; link from `README.md` |
| Add a new dashboard tool | All dashboards read from `scripts/output/` — write a new consumer that reads the same CSVs (Tableau, Looker, Superset, etc.) |

## 11. Closing note

The repository is designed to be a starting point, not a finished product.
Every plant is different: different meter mix, different production cycles,
different regulatory environment, different stakeholder expectations. The
value of this work is in the structured approach — clear data contracts,
conservative validation, honest anomaly handling, multiple dashboard
surfaces — not in any specific number in the sample dataset.

Treat the sample numbers as illustrative. Treat the validation rules as
the minimum, not the maximum. Treat the dashboards as screening tools for
human judgment, not as substitutes for it.

When in doubt, document the assumption, mark the work as unverified, and
let the next reviewer see what you saw. That is how industrial data work
stays trustworthy over time.
